# Teams iCode Talent 演示设计与讨论结论

状态：七个 case 与系统分工已确认，用户已批准并实现 v2 页面演示；真实服务接线及进一步产品细节继续对齐。更新日期：2026 年 10 月 26 日。

本演示以信用卡系统的餐饮返现需求为主线，展示项目 Owner 与项目成员如何通过 Teams、iCode 和 Talent 完成共享、开发、质量检查、验收、追溯与能力演进。本文保存当前已确认的产品边界和页面分工，并单独记录尚待讨论的流程细节；实现进度和运行方式见工程 [README](../README.md)。

基于七个 case 及 Teams 现有实现的一、二级页面方案见 [Teams 与 Talent 演示页面方案](page-map.md)。当前已落地角色导航、项目四页签和任务交付四节点；具体可操作范围和未实现项以页面方案中的“v2 已落地范围”为准。本文件保留已确认 case 与语义，原菜单记录标为首版历史基线。

## 通过 Case 确定页面与流程

讨论的目标是根据演示 case，确定应有哪些页面、每个页面包含哪些内容和能力，以及这些页面在场景中的协作关系。v2 已据此完成页面组织；下文各 case 的目标流程继续作为后续真实接线及细节对齐的依据，不代表每项产品能力均已完整实现。

每个 case 依次明确：业务目标与起点、操作角色与前置条件、关键操作和结果、需要承载这些操作的页面，以及后续环节如何接收结果。页面之间的关系包括入口与返回路径、资产和知识引用、上下文及版本传递、状态回流和角色交接。

| 最终产出 | 需要明确的内容 |
| --- | --- |
| Case 流程 | 谁在什么条件下，从哪里开始，依次做什么，何时完成，结果交给谁 |
| 页面清单与定义 | 所属系统、导航位置、可见角色、展示内容、可执行能力、关键状态、输入与产出 |
| 页面与流程关系 | 页面服务哪些 case，哪些共用或角色独有，如何跳转、传递数据、推进状态并关联证据 |

同一个页面可以服务多个 case，同一个 case 可以跨越 Teams、iCode 和 Talent。页面是否共用或独立，由其承载的操作、信息和角色职责决定。

## 演示范围

- 单独维护 demo 工程，Teams 页面优先直接复用已有布局、组件和交互，只替换演示数据；原实现无法满足的部分明确列出缺口。
- Talent 先制作演示界面，后续再对齐现有系统。
- 业务数据可以 mock，优先保证可操作的端到端流程。
- 保留 iCode 与 OpenCode 的接入展示，接通本机 iCode 启动和历史会话恢复。
- 演示数据、真实历史证据和本机实际连接状态分别标识。工具已启动、上下文已导出、Agent 已读取上下文需要有各自的状态依据。
- 角色统一称为“项目 Owner”和“项目成员”。

## 三个系统的职责

| 系统 | 职责 | 在演示中的主要呈现 |
| --- | --- | --- |
| Teams | 对接各类资产系统，组织项目资产和需求，提供能力共享、作业入口、交付验收、追溯和运营视图 | 代码库和资料关联、知识输入、需求上下文、资源使用、质量结果、交付状态和团队使用情况 |
| iCode | 使用任务上下文执行开发，调用检视、测试和安全扫描等能力，产生执行记录与交付证据，并通过 Teams CLI 和 Skill 同步进度 | 本机启动、会话恢复、上下文读取、开发过程、进度回传、检查与修复 |
| Talent | 根据项目及其已有信息整合知识，基于交付和会话数据分析、评估并改进 Skill 与 Agent | 代码图谱、业务知识、来源关系、会话洞察和能力演进 |

OpenCode 作为 Teams 可接入的另一种执行工具展示。信用卡需求的主要开发演示使用 iCode。

### 知识输入与整合边界

**项目代码、历史需求、设计文档和其他知识材料的输入与关联都在 Teams。Talent 根据 Teams 提供的项目及资产信息做知识整合。**

Owner 准备项目长期使用的代码图谱和知识底座；成员围绕具体需求，在 Teams 中补充材料、选用项目知识和 Skill，形成当次任务的上下文。Talent 的知识界面承担整合结果及其依据的展示。

该边界同样适用于后续页面设计：Teams 项目呈现资产与知识入口，Talent 承载知识整合的专业视图。具体构建状态、版本确认和结果采用步骤仍需逐项对齐。

## 两个角色的职责

| 事项 | 项目 Owner | 项目成员 |
| --- | --- | --- |
| 项目知识 | 准备项目资产，组织存量代码图谱和知识库的构建 | 使用已有知识，补充需求相关材料 |
| 能力共享 | 准备和维护项目可用的能力 | 获取和选用知识、Skill、Agent |
| 需求开发 | 管理需求与分工，关注进展 | 输入需求、准备上下文，在 iCode 中开发 |
| 质量保障 | 维护检视、测试、安全扫描能力及使用要求 | 调用质量能力，查看结果、修复并验证 |
| 交付验收 | 确认交付结果，通过或退回 | 提交变更、检查结果和交付说明 |
| 轨迹追溯 | 查看团队需求、成员作业与会话，追溯交付依据 | 查看自己任务相关的执行记录和问题 |
| 平台自演进 | 分析交付经验，管理 Skill 与 Agent 的改进、评估及采用 | 使用经确认的新版本能力 |
| 运营监控 | 查看团队使用、在线、运行和 Token 情况 | 查看自己的实例、任务和使用情况 |

Owner 和成员具有不同的业务视图；工具接入、个人会话和资源浏览等基础功能共用。

## Owner 工作台的运营重点

Owner 首先需要知道：**有多少人使用 iCode，谁当前在线，谁正在执行任务。** Token 使用情况作为补充信息，能够关联到成员和作业。

当前首页展示方案：

| 区域 | 内容 |
| --- | --- |
| 已使用人数 | 已使用过 iCode 的成员数及其占团队成员的比例 |
| 今日使用人数 | 今天实际使用过 iCode 的成员数 |
| 当前在线人数 | 当前有在线 iCode 实例的成员数 |
| 正在执行人数 | 当前有任务运行中的成员数 |
| 成员使用列表 | 成员、iCode 状态、当前任务、所属项目、最近活跃时间、今日 Token |
| 待 Owner 处理 | 待分配、待验收、需要介入的事项 |

成员状态区分未使用、离线、在线空闲、执行中和等待人工处理。一个成员可以有多个实例，人数按成员去重，实例和会话在明细中查看。

在线判断、有效使用事件、时间窗口及 Token 归集规则仍需细化。演示运营数据可采用 mock，并保持与本机真实连接探测的明确区分。

## 信用卡需求的端到端主线

主线需求为存量信用卡系统的“餐饮消费返现”。现有素材包括 Java 项目代码、历史开发会话和 Skill。

业务样例：持卡人报名活动，餐饮消费满 50 元后按 5% 返现，单笔上限 30 元，每卡最多 5 次。演示以消费 120 元、返现 6 元、重复评估不重复入账为主要验收操作。

| 环节 | 主操作角色 | 工具分工 |
| --- | --- | --- |
| 存量系统知识准备 | Owner | Teams 接入和组织项目资产，Talent 整合代码图谱与知识 |
| 共享和质量能力准备 | Owner | Teams 维护项目可用 Skill、Agent、检视、测试与安全扫描能力 |
| 需求与上下文准备 | 成员 | Teams 输入需求，补充知识和材料，导入或选用 Skill，准备任务上下文 |
| 开发执行 | 成员 | 从 Teams 启动 iCode，读取上下文、开发和修改代码 |
| 检查与修复 | 成员 | iCode 使用质量能力；Teams 呈现检查结果和交付状态 |
| 提交与验收 | 成员提交，Owner 验收 | Teams 提交成果并进行业务验收 |
| 会话与交付追溯 | Owner | Teams 串联需求和执行证据，iCode 提供原始执行记录 |
| Skill 与 Agent 自演进 | Owner | Talent 根据交付数据分析和评估改进，Teams 共享并采用能力成果 |
| 运营监控 | Owner | Teams 呈现团队使用、在线、运行与 Token 数据，贯穿整个流程 |

历史开发中的“未报名导致报名按钮不可达”问题，可作为检查、修复和复测的演示依据。历史检查结果与当前演示执行分别标记；现有素材缺少真实安全扫描报告，质量页面需要保留该状态。

## Case 1 项目知识准备

### 已确认的边界

- 主操作角色为项目 Owner。
- Teams 负责项目代码和各类资料的输入、关联与组织。
- Talent 根据项目及其已有信息整合知识，呈现代码图谱、业务知识和来源关系。
- 成员后续在 Teams 使用项目知识，并补充具体需求的资料与 Skill。

### 待细化的界面流程

以下作为下一轮讨论起点，页面名称和操作步骤尚未全部确定。

| 步骤 | 拟承载位置 | 拟提供功能 |
| --- | --- | --- |
| 准备项目资产 | Teams 项目内的资料与资产区域 | 查看并关联代码库、历史需求、设计文档等信息，识别来源与更新情况 |
| 发起知识整合 | Teams 项目内的知识区域 | 选择资料和范围，交给 Talent 整合 |
| 查看成果 | Teams 状态与摘要，Talent 详细结果 | 查看模块关系、业务规则，以及对应的源码和资料依据 |
| 供项目使用 | Teams 项目知识区域 | 将整合成果关联到项目，供成员准备需求上下文时引用 |

还需要对齐：资料是预先关联还是演示现场添加；资产系统接入与文件上传各展示多少；图谱要展示到模块、调用还是代码位置；Owner 如何确认知识成果；知识更新如何影响正在进行的需求。

## Case 2 需求开发前的准备

### 已确认的边界

- 主操作角色为项目成员，即承担需求的开发人员。
- 成员可以在 Teams 查看需求背景，直接选择项目已有 Skill、用户已有 Skill 与项目 Agent。需求分配、准备和上下文冻结无需先发布项目能力包。
- 资源共享按单个 Skill 或 Agent 发布，发布后供其他人获取或订阅；“我的发布”管理这些资源的共享版本。项目内部可用范围及质量、验收门槛保持各自规则。
- 在启动 iCode 时，将本次需求相关的上下文和选用的 Skill 导入、加载，衔接后续开发。
- 本 case 接续项目知识准备，完成于成员带着需求与所选能力进入 iCode 会话。

### 待细化的界面流程

| 步骤 | 拟承载位置 | 拟提供功能 |
| --- | --- | --- |
| 理解需求 | Teams 项目内的需求详情 | 展示需求背景、目标、范围及关联材料，可引用 Case 1 的项目知识 |
| 选择业务能力 | 需求详情内的 Skill 选择区域 | 展示本需求可用的业务 Skill、用途、来源和版本，允许查看内容并选择 |
| 确认启动内容 | 需求详情的开发准备区域 | 汇总将带入 iCode 的需求背景、选用知识和 Skill，明确对应项目与工作目录 |
| 启动并加载 | Teams 的需求级 iCode 启动入口，进入 iCode | 携带所选内容启动会话，呈现导入和加载结果 |
| 开始开发 | iCode 会话 | 成员能够基于当前需求和已加载能力开展开发，后续执行过程归入下一个 case |

页面归并建议：需求背景、业务 Skill 选择和启动入口可以组成同一个需求详情页的不同区域；Agent 管理直接复用原 Teams 的实例、配置、启动与维护界面。具体页面布局和加载交互尚待对齐。

业务 Skill 根据具体需求选择。进度通过 Teams CLI/Skill 回传，具体管理入口待定；需求准备提供本次项目、需求任务及上下文关联。

还需要对齐：新增业务 Skill 的授权范围与默认选择；是否展示完整的启动上下文预览；新建会话与恢复会话各如何携带内容；Skill 安装或发现、上下文读取的状态如何呈现；导入失败后如何处理。

此处记录的是目标交互。现有 demo 的原生启动、历史恢复和上下文导出能力，需要结合本 case 继续完善需求级选择与加载流程。

## Case 3 需求开发与进度同步

### 已确认的边界

- 主操作角色为项目成员，需求开发的主要活动在 iCode 中完成。
- 开发过程的进度可以通过 Teams CLI 和 Skill 同步给 Teams。
- 进度通过 Teams CLI/Skill 回传，具体管理入口待定；Agent 管理页不承载进度同步。
- 本 case 接续 Case 2 已准备的需求上下文与 iCode 会话。Teams 接收进度后，支持成员查看自己的任务状态，并供 Owner 了解项目进展。

### 待细化的界面流程

| 步骤 | 拟承载位置 | 拟提供功能 |
| --- | --- | --- |
| 开始开发 | iCode 会话 | 使用需求背景、项目知识和已选 Skill 分析并实施需求 |
| 同步进度 | iCode 调用 Teams CLI，配合进度同步 Skill | 将关键阶段、已完成内容、当前工作或阻塞事项关联到 Teams 中的需求任务 |
| 查看任务进展 | Teams 需求或任务详情 | 呈现当前状态、进度更新、更新时间及关联会话，承接 Case 2 的需求详情 |
| 查看项目进展 | Teams Owner 工作台及项目 | 汇总成员任务进展，定位需要介入的事项，并进入对应任务查看详情 |
| 进入后续环节 | iCode 与 Teams 关联任务 | 开发到达相应节点后衔接质量检查或交付，具体节点由后续 case 确定 |

设计上，CLI 承担进度写入接口，Skill 说明如何调用以及何时、以什么内容同步。进度同步的具体管理入口、配置项、启用与加载方式待细化。需求级启动提供项目、需求或任务的关联信息，开发过程中将进度关联到对应的 iCode 会话，供页面回流和后续追溯使用。

页面归并建议：复用 Teams 需求或任务详情中的进度区域、成员工作台和 Owner 项目概览；实际开发操作由 iCode 会话承载。

还需要对齐：同步的关键节点、由成员触发还是由 Agent 按 Skill 自动执行、进度内容与状态定义、同步失败的呈现方式，以及如何关联后续质量检查与交付证据。

此处记录目标交互。v2 已提供基础同步 Skill 与可回写本地演示数据的 CLI；对接真实 Teams CLI、Hook 和会话关联的完整机制仍按后续接线范围推进。

## Case 4 质量与安全检查闭环

### 已确认的边界

- 代码开发完成后，成员使用 Teams 集成的能力进行代码 Review、安全扫描和测试。
- Review、测试和安全扫描由 iCode 发起；Teams 提供接入能力并汇总检查结果。
- Teams 可以通过 Skill 和工具接入这些能力；Owner 负责维护项目可用的质量与安全能力。
- 成员能够查看结果，根据发现的问题修复并再次检查。
- 检查结果关联到本次需求，Owner 后续验收时能够看到需求的功能、安全等达标情况。
- 本 case 承接 Case 3 的开发结果，产出后续交付验收所需的检查结论与依据。

### 待细化的界面流程

| 步骤 | 拟承载位置 | 拟提供功能 |
| --- | --- | --- |
| 准备可用能力 | Teams 企业连接的其他能力配置，项目内引用 | Owner 维护 Review、测试和安全扫描接入的 Skill、工具及使用要求 |
| 发起检查 | iCode 调用 Teams 接入的 Skill 和工具 | 成员针对本次代码变更发起 Review、测试和安全扫描，呈现检查范围和执行状态 |
| 查看结果 | Teams 需求内的质量与安全区域，iCode 接收处理所需结果 | 分别呈现 Review 问题、测试结果、安全发现，支持查看问题位置和报告依据 |
| 修复与复测 | iCode 修复，检查结果回流 Teams | 成员处理问题并重新检查，保留首次发现、修复及复测记录 |
| 查看达标情况 | Teams 需求质量概览及后续验收页面 | Owner 查看功能、安全等各项要求及其结果，打开报告、未解决问题和复测依据 |

页面归并建议：Owner 在企业连接的其他能力配置中维护演示能力；成员在已有需求详情中查看质量与安全结果；Owner 验收页引用同一需求的检查结论和证据。实际代码修复继续在 iCode 完成。

检查结果需要关联需求及其对应的代码版本或变更范围。功能测试、Review 与安全检查分别呈现状态，保留待检查、执行中、达标、未达标，以及执行失败或结果缺失的区别。具体达标规则、阻断条件和状态名称待对齐。

本 case 的检查 Skill 与工具属于 Teams 接入的质量与安全能力；Teams CLI/Skill 提供进度回传支持，具体管理入口待定，需求准备中的业务 Skill 提供业务知识与实施指导。

还需要对齐：各类检查工具的实际执行位置；预置还是由成员选择检查组合；检查范围及报告格式；成员处理问题后的复测方式；Owner 验收时哪些要求必须达标，以及如何展示尚未完成的检查。

## Case 5 交付后的会话上报与轨迹追溯

### 已确认的边界

- 需求交付以后，上报相关的 iCode 会话信息，并呈现 Session 基础轨迹分析数据。
- iCode 已有基础轨迹数据，本 case 以这些已有数据为来源。
- 会话及其轨迹数据在 Teams 项目中能够关联到需求和交付，并支持追溯。
- 主要查看角色为业务 Owner，即本演示的项目 Owner。
- 本 case 承接交付结果；后续 Talent 可以基于相关交付和会话数据开展能力演进。

### 待细化的界面流程

| 步骤 | 拟承载位置 | 拟提供功能 |
| --- | --- | --- |
| 上报交付相关会话 | iCode 与 Teams 的会话数据接入 | 上报会话信息及已有基础轨迹，关联本次项目、需求任务和交付记录 |
| 从需求查看关联记录 | Teams 项目内的需求或交付详情 | 展示关联会话、上报状态、执行时间和交付关系，进入会话详情 |
| 查看 Session 基础分析 | Teams 会话或作业详情 | 基于已有轨迹呈现执行过程、工具操作及相关结果，具体指标与粒度待对齐 |
| 追溯具体依据 | 会话详情中的轨迹和证据区域 | 从分析结果定位原始事件，并关联代码变更、质量检查或交付证据；可关联的内容以数据来源为准 |
| 查看团队交付记录 | Teams 团队作业与追溯 | Owner 按项目、需求、成员查找会话，并进入同一份会话详情 |

页面归并建议：项目需求或交付详情增加关联会话入口；团队作业与追溯承载跨任务列表；两者进入共用的会话详情与基础轨迹分析视图。

追溯关系以“项目 → 需求或任务 → 交付记录 → iCode 会话 → 轨迹事件及相关证据”为主线。同一需求可能关联多次会话，具体会话和交付之间的关联规则待细化。

Case 3 提供开发过程中的进度同步；本 case 提供交付相关会话、基础分析和可追溯记录。两者通过项目、需求任务及会话的关联衔接。

还需要对齐：上报发生在提交交付还是验收完成后、由谁触发；通过哪些已有接入能力上报；会话及轨迹上报的范围；iCode 现有基础数据能够支持哪些分析；一个需求关联多个会话时如何呈现；代码与报告证据如何定位和打开。

## Case 6 Talent 平台级分析与 iCode 自演进

### 已确认的边界

- 本 case 属于 Talent 的平台级能力，主要操作角色为项目 Owner。
- 分析范围支持单个需求，以及同一项目内多个需求的相关轨迹和信息。
- Talent 通过轨迹分析与知识挖掘，为 iCode 的自演进产出改进。
- 改进对象包括 Agent 配置定义和业务 Skill。
- 输入承接 Case 5 已上报并关联的会话轨迹，也结合项目知识、需求及交付结果理解业务背景。

### 待细化的界面流程

| 步骤 | 拟承载位置 | 拟提供功能 |
| --- | --- | --- |
| 选择分析范围 | Talent 分析入口 | 选择单条需求，或项目内多条需求，查看对应会话、轨迹和已有项目资料 |
| 分析轨迹与挖掘知识 | Talent 分析结果 | 识别执行中的问题、可复用经验和业务规则；多需求分析呈现共性及差异，并关联具体来源 |
| 形成改进候选 | Talent 能力演进 | 将发现关联到 Agent 配置定义或业务 Skill，展示改进理由、原内容、候选变更和依据 |
| 评估候选 | Talent 评估视图 | 比较改进前后的表现，分别评估 Agent 与 Skill 改动，具体方法与用例待定 |
| 确认产物并供后续使用 | Talent 发布结果，Teams 能力与资源入口 | Owner 确认改进结果，形成可采用的 Agent 定义或业务 Skill 版本，由后续 iCode 作业使用 |

页面归并建议：Talent 提供分析范围选择、分析与挖掘结果、改进候选详情及评估发布视图；这些功能是否合并为一个分析任务详情或拆页，后续按操作流程确定。

Agent 配置定义和业务 Skill 作为两类改进产物分别呈现。Agent 改进可以涉及执行流程、工具使用与完成判定要求；业务 Skill 改进可以涉及业务规则、领域处理步骤与检查要求。具体改动内容以所选需求和轨迹的分析结果为依据。

产物回到 Teams 的归属仍需细化：Agent 配置定义通过 Agent 管理或共享能力入口采用，业务 Skill 通过资源市场和项目需求准备采用。后续 iCode 作业使用已采用版本；历史会话保留其原有上下文和能力版本，便于比较与追溯。

本 case 的平台级含义是分析和演进能力可服务不同需求与项目；当前明确的聚合分析范围为同一项目内的多个需求。跨项目聚合的规则尚未讨论。

还需要对齐：分析范围的选择方式；单需求与多需求各展示哪些发现；知识挖掘产物如何沉淀和关联项目知识；Agent 与业务 Skill 候选如何编辑、评估和确认；发布与采用入口；如何在后续需求中展示改进效果。
