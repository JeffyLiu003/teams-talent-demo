# ID 编码规范

本规范定义 SDLC 全链路各环节工件的 ID 编码规则，覆盖命名规则、生成规则与关联规则。所有审计证据包中的 ID 须符合本规范。

## 1. ID 类型总览

| 类型 | 前缀 | 格式 | 示例 | 说明 |
|------|------|------|------|------|
| 需求 | REQ | REQ-YYYY-xxxx | REQ-2026-0001 | 业务需求说明书 |
| 用户故事 | US | US-YYYY-xxxx | US-2026-0001 | 敏捷用户故事（含验收标准） |
| 合并请求 | MR | MR-xxxx | MR-789 | 代码合并请求（Git 平台原生 ID） |
| 测试用例 | TC | TC-YYYY-xxxx | TC-2026-0001 | 测试用例（含执行报告） |
| 变更单 | CHG | CHG-YYYY-xxxx | CHG-2026-0012 | 变更申请单（RFC） |
| 发布单 | REL | REL-YYYY-xxxx | REL-2026-0034 | 发布单（含灰度/回滚记录） |
| 事后复盘 | PIR | PIR-YYYY-xxxx | PIR-2026-0005 | 事后复盘报告（Post-Incident Review） |
| 业务规则 | BR | BR-{{领域}}-xxx | BR-PAY-001 | 业务规则（跨技能引用） |
| 审计证据包 | EV | EV-YYYY-xxxx | EV-2026-0007 | 审计证据包编号 |

> **CHG 与 RFC 的关系**：本规范默认变更环节 ID 前缀为 `CHG`（Change），兼容历史 `RFC` 前缀。证据包中以 `CHG` 为准，`RFC-xxx` 须映射为 `CHG-xxx` 并保留映射记录。

## 2. 命名规则

### 2.1 前缀

- 前缀必须为大写字母（A-Z），长度 2-4 字符
- 前缀必须为本规范定义的类型之一，禁止自创前缀
- 前缀与序列号之间以连字符 `-` 分隔

### 2.2 年份

- 年份为 4 位数字（YYYY），取工件创建年份
- 同一链路内年份须一致或递增（跨年项目除外，但须说明）
- MR 类型不含年份（沿用 Git 平台原生 ID，如 `MR-789`）

### 2.3 序列号

- 序列号为 4 位数字（xxxx），从 0001 开始
- 同前缀 + 同年份的序列号全局唯一（CHG/REQ/US/TC/REL/PIR/EV）
- MR 的序列号沿用 Git 平台原生 ID，不做补零（如 `MR-789` 而非 `MR-0789`）
- 业务规则 BR 的序列号为 3 位数字，按领域分段（如 `BR-PAY-001` 为支付领域第 1 条）

### 2.4 分隔符

- 各段之间使用连字符 `-` 分隔
- 禁止使用下划线 `_`、空格、点 `.` 作为分隔符

## 3. 生成规则

### 3.1 生成时机

| 类型 | 生成时机 | 生成方 |
|------|---------|--------|
| REQ | 需求说明书创建时 | 需求平台自动生成 |
| US | 用户故事创建时 | 敏捷平台自动生成 |
| MR | 合并请求创建时 | Git 平台自动生成 |
| TC | 测试用例创建时 | 测试平台自动生成 |
| CHG | 变更单提交时 | 变更管理平台自动生成 |
| REL | 发布单创建时 | 发布平台自动生成 |
| PIR | 复盘报告创建时 | PIR 平台自动生成（或人工编号） |
| BR | 业务规则入库时 | 业务架构团队人工编号 |
| EV | 证据包生成时 | audit-evidence 技能生成 |

### 3.2 唯一性保证

- 同前缀 + 同年份的序列号由平台保证唯一（数据库唯一约束）
- 跨平台 ID 冲突时，由平台间同步机制保证（如 REQ 与 US 不在同一平台，但年份+序列号组合不冲突）
- MR 的 ID 由 Git 平台保证仓库内唯一；跨仓库 MR 须在证据包中标注仓库标识

### 3.3 编号回收

- 已生成的 ID 不得回收复用（即使工件被删除）
- 删除工件时，平台保留 ID 记录并标记为"已删除"
- 证据包中引用已删除工件的 ID 须在缺失原因中说明

## 4. 关联规则

### 4.1 全链路关联路径

```
REQ → US → MR → TC → CHG → REL → PIR
```

每相邻环节存在关联关系：
- US 的"需求字段"指向 REQ
- MR 的"关联故事字段"指向 US
- TC 的"关联故事字段"指向 US（或直接指向 REQ）
- CHG 的"关联 MR 字段"指向 MR（可多个）
- REL 的"关联变更字段"指向 CHG（可多个）
- PIR 的"关联发布字段"指向 REL

### 4.2 关联字段规范

| 上游 | 下游 | 关联字段 | 基数 |
|------|------|---------|------|
| REQ | US | `requirement_id` | 1:N（一个需求可拆分多个故事） |
| US | MR | `story_id` | 1:N（一个故事可多次合并） |
| US | TC | `story_id` | 1:N（一个故事可有多个用例） |
| MR | CHG | `merge_request_id` | N:1（多个 MR 可合并到一个变更单） |
| CHG | REL | `change_id` | N:1（多个变更可打包到一个发布） |
| REL | PIR | `release_id` | 1:0..1（发布可有 0 或 1 个复盘） |

### 4.3 跨环节追溯

- 正向追溯：REQ → US → MR → TC → CHG → REL → PIR（需求到生产）
- 逆向追溯：PIR → REL → CHG → MR → TC → US → REQ（生产到需求）
- 横向追溯：TC ↔ MR（测试用例与代码变更的双向覆盖）

## 5. ID 校验规则

`scripts/trace_check.py` 当前仅校验 ID 非空，不校验 ID 编码规范。以下为规划中的校验规则（人工校验或后续脚本版本支持）：

| 校验项 | 规则 | 失败处理 |
|--------|------|---------|
| 前缀合法 | 必须为 REQ/US/MR/TC/CHG/REL/PIR/BR/EV 之一 | 标记缺失，须修正 |
| 格式合法 | REQ/US/TC/CHG/REL/PIR/EV 须为 `前缀-YYYY-xxxx`；MR 须为 `MR-数字`；BR 须为 `BR-领域-xxx` | 标记格式错误，须修正 |
| 年份一致 | 同一链路内年份须一致或递增（跨年项目除外） | 警告，须说明 |
| 序列号唯一 | 同前缀+同年份序列号全局唯一 | 标记重复，须修正 |
| 关联字段完整 | 相邻环节 ID 关联字段非空 | 断链须记录原因 |

## 6. 示例

### 6.1 完整链路示例

```
REQ-2026-0001 (需求: 个人网银转账限额调整)
  └─ US-2026-0001 (故事: 限额参数配置页)
      ├─ MR-789 (MR: 限额参数配置页前端)
      ├─ MR-790 (MR: 限额参数配置页后端)
      └─ TC-2026-0001 (测试: 限额参数配置用例)
          └─ CHG-2026-0012 (变更: 限额参数配置上线)
              └─ REL-2026-0034 (发布: 2026年第34次生产发布)
                  └─ PIR-2026-0005 (复盘: 发布后限额异常复盘)
```

### 6.2 多需求合并发布示例

```
REQ-2026-0001 ─┐
REQ-2026-0002 ─┤
REQ-2026-0003 ─┴─ CHG-2026-0012 ─ REL-2026-0034 ─ PIR-2026-0005
```

### 6.3 CHG/RFC 映射示例

```
历史 ID: RFC-012
当前 ID: CHG-2026-0012
映射记录: RFC-012 ↔ CHG-2026-0012（变更管理平台迁移，2026-01-01）
```

## 7. 全链路追溯

全链路：REQ → US → MR → TC → CHG → REL → PIR

| 环节 | 必填 | 缺失处理 |
|------|------|---------|
| REQ | L2+ | 缺失须说明（不适用/暂缺/替代证据/已丢失） |
| US | L2+ | 缺失须说明 |
| MR | L2+ | 缺失须说明 |
| TC | L2+ | 缺失须说明 |
| CHG | L2+ | 缺失须说明（纯需求评审可标注"不适用"） |
| REL | L2+ | 缺失须说明（发布前评审可标注"暂缺"） |
| PIR | L2+ | 缺失须说明（无事故可标注"不适用"） |

> 详细证据标准见 `references/evidence-standards.md`。
