# ADR-005: 跨服务一致性与幂等策略

| 项 | 内容 |
|----|------|
| 编号 | ADR-005 |
| 日期 | 2026-10-25 |
| 状态 | 已接受 |
| 关联需求 | BR-BILL-05、BR-POST-06、BR-POST-08、NR-POST-01 |

## 背景

账单支付与日终入账需要同时写"交易"和"账户余额"。遗留系统通过 CICS 单事务保证原子性；
拆分后两次写操作位于不同数据库，必须选择一致性方案，并定义失败与重试语义。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| 方案A：本地事务 + 同步调用 + 失败回滚 + 幂等键 | 先写本地交易（状态 PENDING），调下游成功后置为 POSTED；失败则本地回滚；每笔交易带唯一业务号 | 实现简单；无中间件；失败可见 | 依赖下游可用性；极短窗口存在"下游已执行、本地回滚"的不一致 |
| 方案B：事务性 Outbox + 消息队列最终一致 | 本地写交易与 outbox，异步投递账户记账；消费端幂等 | 解耦；下游故障可重试 | 需消息中间件与对账作业；演示环境复杂度高 |
| 方案C：Saga 编排 + 补偿事务 | 显式补偿（反向记账） | 长事务可恢复 | 补偿规则复杂；对账与审计成本高 |

## 量化权衡表

| 方案 | 实现成本 | 性能开销 | 运维时效 | 审计性 | 风险 |
|---|---|---|---|---|---|
| A | 低 | 低（1 次同步调用） | 秒级失败可见 | 高（交易状态机可查） | 中（短窗口不一致） |
| B | 高 | 中（异步 + 消费延迟） | 分钟级最终一致 | 高（outbox 可审计） | 低（需对账） |
| C | 很高 | 中高 | 分钟级 | 高 | 中 |

## 决策

本期采用方案 A，并落实三项约束：

1. 每笔交易以 `transactionId` 为幂等键，重复提交返回既有结果（NR-POST-01）。
2. 账单支付：先生成交易（PENDING）→ 调 `POST /accounts/{id}/payments` → 本地置 POSTED；
   下游失败则本地事务回滚，客户端收到 503 并可用同一请求重试。
3. 入账：单笔"类别累计 + 账户记账"失败时，该笔进入 `REJECTED` 并记录原因，不中断整批；
   运行结果返回 `processed/posted/rejected` 计数（对齐 BR-POST-08 返回码 4 的语义）。

方案 B 作为下一阶段演进（Outbox + Kafka/RabbitMQ），届时账户侧需支持幂等消费。

## 理由

演示与首期上线以"可观测、可重试、可对账"优先；同步调用链路短，失败概率与恢复成本可控。
对账作业以 `transaction` 与 `account` 的日终快照比对兜底（见回退路径）。

## 后果（影响与回退路径）

- 影响：下游不可用时账单支付返回 503；入账批处理报告部分成功。
- 回退：若出现跨库不一致，按日终对账差异执行反向记账（冲正）并以 `transaction` 为权威；
  后续切换方案 B 时保留现有 API 与幂等键语义。
