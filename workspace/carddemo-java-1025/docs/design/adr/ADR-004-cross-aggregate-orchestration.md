# ADR-004: 跨聚合用例的编排归属（账户视图 / 账户维护 / 账单支付）

| 项 | 内容 |
|----|------|
| 编号 | ADR-004 |
| 日期 | 2026-10-25 |
| 状态 | 已接受 |
| 关联需求 | BR-ACCT-07/08、BR-BILL-01..05、BR-TRN-01..06 |

## 背景

遗留屏幕把多个聚合放在同一个事务里：

1. `COACTUPC` 一个屏幕同时修改 Account 与 Customer（`READ UPDATE` 两文件 + `REWRITE` 两次）。
2. `COACTVWC` 一个屏幕展示 Account + Customer + Card 映射。
3. `COBIL00C` 一个事务里写 TRANSACT 并扣减 ACCTDAT 余额。
4. `CBTRN02C` 一个批处理里写 TRANSACT、TCATBALF 并更新 ACCTDAT。

微服务拆分后不能保留跨库事务，需要明确"谁编排、谁执行、失败怎么办"。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| 方案A：调用方（前端/BFF）组合查询；资金类用例由 transaction-service 编排 | 查询组合在边缘；写用例集中在拥有"交易"聚合的服务 | 职责清晰；事务边界最小；贴合业务（支付是交易上下文用例） | 前端需多次调用；编排服务依赖下游 |
| 方案B：每个服务暴露"聚合写"接口，由前端编排 | 服务纯 CRUD | 服务简单 | 业务规则泄漏到前端；无法保证一致性；审计困难 |
| 方案C：建立独立 BFF/编排服务 | 新增第 7 个服务 | 前端只调一次 | 多一跳与一套部署；演示项目收益低 |

## 量化权衡表

| 方案 | 实现成本 | 性能开销 | 运维时效 | 审计性 | 风险 |
|---|---|---|---|---|---|
| A | 中 | 中（2–3 次调用） | 即时 | 高（每个写操作有明确属主） | 中（需要补偿） |
| B | 低 | 低 | 即时 | 低 | 高（一致性无保障） |
| C | 高 | 中高 | 即时 | 高 | 中 |

## 决策

采用方案 A：

- **查询**：账户视图由调用方组合 `GET /accounts/{id}` + `GET /customers/{cid}` + `GET /cards/by-account/{aid}`。
- **账户维护**：拆为 `PUT /accounts/{id}`（账户字段）与 `PUT /customers/{id}`（客户字段）两个用例，
  不再有跨聚合事务；UI 分步提交并按错误码提示。
- **账单支付**：`transaction-service` 作为用例编排者（读取账户 → 生成支付交易 → 调账户扣款），
  本地事务内的写操作失败即回滚。
- **日终入账**：`transaction-service` 编排，"校验 + 类别累计"在本地，"账户余额变更"调 account-service。

## 理由

1. 支付与入账的权威记录是交易（TRANSACT），账户余额是可重算的派生状态，编排应归交易上下文。
2. 账户与客户是两个独立生命周期（客户可有多账户），强行放在一个事务里是遗留屏幕的实现耦合。
3. 授权上下文需要"读账户快照 + 写自己的待授权汇总"，天然适合自己编排。

## 后果（影响与回退路径）

- 影响：UI/前端需要组合调用；服务间增加网络失败分支（统一 503 + 重试）。
- 回退：若前端无法组合，可新增只读 BFF（方案 C），既有 API 不变。
