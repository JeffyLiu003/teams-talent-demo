# 门禁定义（G1–G8）

银行交付流水线采用 G1–G8 八阶段门禁模型，覆盖从需求签字到实施后复核的全生命周期。每个门禁定义以下要素：

- **审批人**：门禁放行的责任角色
- **触发条件**：进入该门禁评审的前置条件
- **必检产出物**：门禁通过必须存在的产出物清单
- **通过标准**：可计算/可验证的放行标准
- **常见缺失模式**：典型缺失场景与规避
- **自动采集源**：L3 状态自动采集的数据源（ALM/CI/ITSM）

---

## G1 需求签字

| 维度 | 内容 |
|------|------|
| 审批人 | 业务负责人 |
| 触发条件 | 需求说明书完成 BA 自检（spec_completeness.py 通过）；澄清问题清单已闭环 |
| 必检产出物 | 需求说明书（含功能/非功能/业务规则/合规标注）、澄清问题清单（已闭环）、业务规则溯源清单 |
| 通过标准 | 需求与验收标准完整可测；每条业务规则有来源；非功能需求可量化；模糊词扫描无 high 严重度 |
| 常见缺失模式 | 业务规则无来源；非功能需求未量化；澄清问题未闭环即送审 |
| 自动采集源 | ALM（需求条目状态 = 已签字）、文档库（需求说明书版本对齐） |

## G2 设计批准

| 维度 | 内容 |
|------|------|
| 审批人 | ARB（架构评审委员会） |
| 触发条件 | G1 已通过；设计文档与 ADR 完成；影响分析完成 |
| 必检产出物 | 设计文档（HLD/LLD）、ADR（架构决策记录）、影响分析（含存量系统/接口/数据） |
| 通过标准 | 设计合规（符合行内架构规范）；影响评估完成（覆盖受影响系统/接口/数据）；ADR 状态 = 已接受 |
| 常见缺失模式 | 影响分析遗漏受影响系统；ADR 状态停留在"提案"；设计未覆盖非功能需求 |
| 自动采集源 | ALM（设计条目状态）、文档库（设计文档版本）、ADR 仓库（状态字段） |

## G3 代码评审

| 维度 | 内容 |
|------|------|
| 审批人 | 资深工程师（非代码作者，满足 SoD） |
| 触发条件 | G2 已通过；MR 已提交；静态扫描已执行 |
| 必检产出物 | MR（含变更说明）、静态扫描报告、单元测试报告 |
| 通过标准 | 静态检查通过（无 fatal/high）；评审意见 100% 闭环（resolved/wontfix 有说明）；单元测试覆盖率达标 |
| 常见缺失模式 | MR 无变更说明；评审意见未闭环即合并；静态扫描 fatal 未处置 |
| 自动采集源 | CI（构建状态、静态扫描结果、单元测试覆盖率）、代码仓库（MR 状态、评审意见） |

## G4 测试退出

| 维度 | 内容 |
|------|------|
| 审批人 | 测试负责人 |
| 触发条件 | G3 已通过；测试用例执行完成；缺陷收敛达标 |
| 必检产出物 | 测试退出报告、缺陷清单、性能基线对比 |
| 通过标准 | 测试执行率 ≥ 100%（用例全部执行）；遗留缺陷达标（无 fatal/high 未关闭，medium/low 有处置计划）；性能基线达标（p95/TPS/错误率符合目标） |
| 常见缺失模式 | 用例未全执行即退出；fatal/high 缺陷未关闭；性能基线缺失对比 |
| 自动采集源 | ALM（测试用例执行率、缺陷状态）、性能测试平台（p95/TPS/错误率） |

## G5 安全放行

| 维度 | 内容 |
|------|------|
| 审批人 | 安全负责人 |
| 触发条件 | G4 已通过；安全扫描完成；漏洞处置完成 |
| 必检产出物 | 安全放行意见、漏洞处置清单、渗透测试报告（高风险场景必填） |
| 通过标准 | 中高风险漏洞清零或豁免（豁免须有书面理由与补偿控制）；安全扫描无 fatal；渗透测试无 critical |
| 常见缺失模式 | 中高风险漏洞未处置即放行；豁免无书面理由；渗透测试缺失 |
| 自动采集源 | 安全平台（漏洞状态、扫描结果）、ITSM（豁免工单） |

## G6 变更批准

| 维度 | 内容 |
|------|------|
| 审批人 | CAB（变更顾问委员会） |
| 触发条件 | G5 已通过；RFC 完整；风险评估完成 |
| 必检产出物 | RFC（变更请求）、风险评估、回滚方案、发布计划、影响分析 |
| 通过标准 | 风险评估完成（风险等级明确）；回滚方案可行（步骤完整+验证+时限）；窗口可用（无冻结期冲突）；CAB 表决通过 |
| 常见缺失模式 | RFC 字段缺失；回滚方案无验证步骤；窗口与冻结期冲突；风险等级未定 |
| 自动采集源 | ITSM（RFC 状态、变更窗口、冻结期日历）、风险评估工具 |

## G7 发布执行

| 维度 | 内容 |
|------|------|
| 审批人 | 双人复核（发布执行人 + 监督人，满足 SoD） |
| 触发条件 | G6 已通过；部署手册完整；灰度策略明确 |
| 必检产出物 | 发布记录、部署手册、灰度发布结果、监控告警快照 |
| 通过标准 | 检查单完成（前置/部署/后置三段全勾选）；灰度通过（无异常告警）；监控基线稳定 |
| 常见缺失模式 | 检查单未全勾选即放行；灰度跳过；监控告警未确认 |
| 自动采集源 | CI/CD（部署流水线状态）、监控平台（告警快照）、ITSM（发布工单） |

## G8 实施后复核

| 维度 | 内容 |
|------|------|
| 审批人 | 变更经理 |
| 触发条件 | G7 已通过；PIR 完成；监控稳定期 ≥ 24h（或业务约定时长） |
| 必检产出物 | PIR（实施后复核报告）、监控稳定期数据、业务验收确认 |
| 通过标准 | PIR 闭环（覆盖目标达成/问题/经验/改进项）；证据归档；业务验收通过；监控稳定期无 critical 告警 |
| 常见缺失模式 | PIR 流于形式无改进项；证据未归档；业务验收未签字 |
| 自动采集源 | ITSM（PIR 工单状态）、监控平台（稳定期告警）、文档库（归档证据） |

## 门禁通用规则

1. **顺序性**：G1 → G2 → ... → G8 顺序执行，前一阶段未通过不得进入下一阶段（除并行评审场景外，须经 PMO 特批）
2. **状态值统一**：通过 / 缺失 / 待办 / 不适用（N/A）；N/A 须注明依据（如"本变更不涉及代码改动，G3 不适用"）
3. **缺失项闭环**：缺失项必须有原因 + 责任人 + 预计闭环时间（早于下一阶段评审时间）
4. **高风险门禁替代证据**：G5/G6 等高风险门禁缺失时，须提供替代证据或缓解措施并经合规确认
5. **自动采集优先**：能从 ALM/CI/ITSM 自动采集的状态不靠人工录入；人工录入须有责任人签字
6. **审批人留痕**：每门禁审批人姓名/角色/时间/意见四要素齐全；L3 禁止"全量同意"无意见通过

## 与脚本的对应

| 脚本 | 对应门禁 | 用途 |
|------|---------|------|
| `scripts/gate_collect.py` | G1–G8 全部 | 从状态 JSON 汇总门禁状态，输出通过/缺失清单；退出码 0=全部通过，2=存在缺失，3=参数错误 |

> 脚本仅消费 `status` 字段做通过/缺失判定（`通过` / `PASS` 视为通过）；其他字段（approver/evidence_url/collected_from）由模板的 L3 字段承接人工或集成层补充。
